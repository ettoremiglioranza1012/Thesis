\chapter{Conclusions}
\label{ch:conclusions}

\section{Summary of the Work}
\label{sec:conclusions_summary}

Chapter~\ref{ch:introduction} formulated three research questions under a single constraint: an LLM performing semantic routing on natural-language workforce requests, with personal data excluded from its context, while preserving the operational correctness an operator would need to act on the result without a manual check. The chapters that follow addressed these questions empirically, through the implementation and validation of a working system, rather than through architectural argument alone.

The first question concerned the division of responsibility between client, anonymisation layer, LLM, and business-logic server required to minimise PII exposure structurally rather than by policy. Chapter~\ref{ch:architecture}'s four-service topology provides this division. The MCP client anonymises a prompt through the Anonymisation Service before it reaches the server; GLiNER detects entities, the Anonymisation Service replaces them with typed, numbered tokens and stores the mapping in Redis under a context identifier; \texttt{ask\_antares} receives only the tokenised text and the context identifier; \texttt{JobTools} restores the original values only after Claude has produced its routing decision, server-side, at the point where the corresponding business operation executes (Section~\ref{sec:arch_privacy_by_design}). By construction, no component upstream of \texttt{JobTools} is given both a token and the value it represents; the model only ever receives whatever the detection layer chose to tokenise. Chapter~\ref{ch:usecases} tested what that design actually delivers in practice, which depends on detection recall and not only on the topology: scanning the literal text Claude received across fifty test prompts identified real PII in two of them, and both instances trace to a specific missed detection by GLiNER, an entity the pipeline never tokenised in the first place, rather than to a leak of an already-tokenised value (Section~\ref{subsec:usecases_llm_audit}).

The second question concerned the detection layer: whether a zero-shot, multilingual NER model could reach the recall required for Italian business text, after the rule-based alternative evaluated earlier in the project, Presidio, had proven inadequate for this purpose (Section~\ref{subsec:impl_gliner_pivot}). Across 82 labelled entity spans in 50 prompts, GLiNER reached 93.8\% precision and 91.5\% recall on the coverage metric, the metric that determines whether PII can leak into the LLM's context at all (Table~\ref{tab:gliner_metrics}). The seven spans it missed were not evenly distributed across error types: four shared a single cause, Italian date-range phrasing of the form ``dal X al Y'', which Table~\ref{tab:gliner_fn} records as a specific, identified weakness rather than an unexplained residual within an aggregate score.

The third question concerned the cost, if any, that reversible tokenisation imposes on correctness. Twelve end-to-end test cases spanning the three use cases, each verified against an independently written reference implementation that shares no code with the system under test, matched in full (Tables~\ref{tab:uca_e2e}, \ref{tab:ucb_e2e}, \ref{tab:ucc_e2e}). Routing accuracy, the property that has to hold on tokenised rather than real input, was measured at 95.2\% under the log-diffing detection method used in this evaluation. The single discrepancy was checked by hand against the response text rather than re-run: it shows Claude selected the correct tool and then exited on a legitimate business-logic failure before the log file the detection method relies on was written, which is a limitation of that method on this one prompt, not evidence of an incorrect routing decision (Table~\ref{tab:routing_summary}). Twenty-one prompts, run five times each at Claude's configured sampling temperature of 1.0, selected the same tool on every repetition. On this test set, the privacy layer did not measurably degrade correctness, and this claim now rests on direct measurement rather than on the internal consistency of the architecture's design.

The validation process also identified an inaccuracy in an earlier chapter. Chapter~\ref{ch:architecture}'s worked tokenisation example originally described GLiNER splitting the canonical Bergamo prompt into two location tokens; the routing data collected for Table~\ref{tab:routing_summary} showed that it in fact produces three, fragmenting a compound site descriptor that had been described as a single unit. The correction itself is minor, but it illustrates a more general point: a description of system behaviour that had not been checked against the running system, even after the architecture chapter had already been written and reviewed, contained an error that only direct observation of the system revealed.

These results should not be read without qualification. GLiNER's coverage recall of 91.5\% is not a marginal detail; it defines the practical limit of the privacy guarantee this architecture provides, since any entity GLiNER fails to detect reaches Claude unmasked, a relationship Section~\ref{subsec:usecases_llm_audit} establishes directly rather than by inference. The Redis context store has no configured time-to-live, so a request that fails before completion leaves its token mapping in memory indefinitely; this gap was left open deliberately, appropriate to a proof of concept rather than a production deployment (Section~\ref{sec:discussion_security_complexity}). The substitute-finding branch of Use Case C, which activates once a colleague is recorded as absent, was not exercised during this validation run because the run took place outside the mock dataset's absence-ticket date window (Section~\ref{sec:usecases_holiday_request}). Finally, every result reported in this thesis was obtained against a mock Miorelli backend, never against the production tenant, a scope decision agreed with the host company in order to concentrate the internship's limited time on the privacy layer rather than dividing it with a live system integration (Section~\ref{sec:intro_contributions}).

\section{Final Remarks on Enterprise AI Adoption}
\label{sec:conclusions_final_remarks}

The GDPR draws a clear distinction between pseudonymisation and anonymisation, and Section~\ref{subsec:background_pii_definitions} applies it to this architecture directly: replacing a name with \texttt{<PERSON\_0001>} does not remove personal data from the system, it relocates that data to a location the system controls, the Redis mapping, rather than to one it does not, the external model provider's infrastructure~\cite{gdpr2016}. This distinction has a direct implication for how the results of this thesis should be generalised beyond Antares AI. Reducing PII exposure to the LLM does not eliminate the underlying privacy obligation; it shifts the obligation to wherever the token map is stored, and that location requires the same standard of engineering, retention control, and access management that the original data would have required. The absence of a configured time-to-live on this project's own Redis store (Section~\ref{sec:discussion_security_complexity}) is a concrete instance of this: a structurally correct boundary between the model and sensitive data does not, on its own, guarantee that what sits behind the boundary is adequately governed.

The Model Context Protocol's separation of host, server, and model roles~\cite{anthropic2024mcp} provided an existing point at which this boundary could be placed, rather than requiring one to be designed from first principles. This thesis's contribution to that observation is empirical: Section~\ref{sec:usecases_validation} confirms that the enforcement point holds under measurement, and not only under the protocol specification's own description of it. A systematic review of the MCP ecosystem found that few deployed systems implement the safeguards the protocol makes available~\cite{hou2025mcpsecurity}. Antares AI satisfies that recommendation for the specific property it was built to test, isolation of PII from the model's context, while sharing the same unresolved operational gaps, retention policy, encryption at rest, and access control over local log files, that the same literature identifies as common across MCP deployments generally.

Section~\ref{sec:background_sota} found no reviewed system that combines local detection, reversible tokenisation, external semantic routing, and deterministic server-side execution together with a validated correctness benchmark. Antares AI addresses part of that gap, not all of it. The validation reported in Chapter~\ref{ch:usecases} covers three use cases against a mock dataset constructed to reproduce one company's platform, not a general-purpose benchmark comparable across domains. What generalises beyond this specific scope is not the accuracy figures themselves, which are properties of this dataset and this prompt set, but the underlying approach: detect PII locally, tokenise it reversibly, route on tokens externally, execute and de-anonymise only within a trusted boundary, and measure the detection layer's recall directly rather than assume it. This is the part of the work a different implementation, in a different domain or against a different backend, could reasonably be expected to reuse.

The replacement of Presidio with GLiNER, documented in Section~\ref{subsec:impl_gliner_pivot}, is relevant here beyond its immediate technical justification. The initial architecture had already been approved with Presidio as the detection layer; it was changed only after the company's actual use cases became available and Presidio's recall on Italian business text proved insufficient. Applying privacy-by-design~\cite{cavoukian2009privacy} in practice, as distinct from stating it as a principle, required discarding an already-approved component once it was tested against real input and found inadequate. Use Case C's three-way authorisation gate illustrates a related point: its correctness against the mock backend depends on a caller identity that is safe only because it is hardcoded rather than resolved, and Section~\ref{sec:discussion_production_migration} identifies this as the one dependency the current architecture cannot defer once a real identity provider is introduced. Both observations suggest that the practical difficulty of applying privacy-by-design in an enterprise setting lies less in the initial architectural design than in the willingness to revise components once they are tested against real data and real operational constraints.

The findings of this thesis support a narrower claim than a general statement that privacy and capability are compatible in LLM-based enterprise systems. They support the claim that the two properties are compatible under three specific conditions: the boundary between the model and sensitive data is structural rather than assumed, the detection layer's recall is measured rather than taken for granted, and the business logic behind the boundary remains deterministic and auditable rather than delegated to the model. Antares AI is a single system, validated on one company's workforce management platform, in which these three conditions were met and verified. Whether the same holds for other domains, languages, or model providers is a question this thesis cannot answer directly; it can only report that the approach described here is specific enough to be tested against those cases in future work.
