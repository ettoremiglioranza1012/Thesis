\chapter{Discussion and Future Work}
\label{ch:discussion}

This chapter reflects on what the implementation and validation described in the previous chapters actually established, and where the current system falls short of what running in production would require. Section~\ref{sec:discussion_security_complexity} weighs the security properties the anonymisation pipeline provides against the architectural complexity it adds, including the prototype-scope gaps already flagged in earlier chapters rather than solved problems. Section~\ref{sec:discussion_validation_limitations} separates what typed schemas and deterministic code actually guarantee from what was measured, and names the routing model's temperature setting as an open methodological question rather than an implicit assumption. Section~\ref{sec:discussion_production_migration} discusses what remains before the mock Miorelli backend can be replaced with the production system. Section~\ref{sec:discussion_redis_scalability} considers how the Redis-based context store would need to change under concurrent, multi-tenant load. Section~\ref{sec:discussion_future_extensions} closes the chapter with two possible extensions: multimodal (voice) input and locally hosted models.

\section{Security vs.\ Complexity Trade-offs}
\label{sec:discussion_security_complexity}

The anonymisation pipeline's privacy protections stop short of what a production deployment would require in two related places. The Redis context holding token-to-entity mappings (Section~\ref{subsec:impl_token_reinjection}) has no time-to-live configured. A mapping is removed only when \texttt{Pop} is actually called during a successful server-side deanonymisation; a request that errors out before that point, or a client session that is abandoned mid-flow, leaves its mapping in Redis with no expiry, bounded in practice only by the process's own lifetime. The per-request reports written to \texttt{JobTools}'s local \texttt{logs/} directory (Section~\ref{sec:impl_jobtools}) sit on the other side of the same gap: they contain real names, phone numbers, and distances, are never transmitted anywhere and were never intended to be, but they are also an unencrypted, access-uncontrolled, retention-unmanaged record on local disk.

Neither gap was addressed during the internship, and that was a deliberate scope decision rather than an oversight. The system runs as a local proof of concept: Redis has no persistence volume mounted, so every context is cleared the moment the container stops regardless of whether \texttt{Pop} ever ran, and the log files exist on a machine no one outside the development team has access to. What the internship needed to demonstrate was that reversible pseudonymisation and its MCP-based orchestration work correctly end to end, not that the system already meets the retention and access-control standards a production deployment would be held to. Closing this gap would mean configuring an explicit time-to-live on the Redis context matched to the maximum reasonable lifetime of a single request, defining a retention and deletion policy for the log files, and encrypting them at rest; none of this requires redesigning the architecture described in Chapter~\ref{ch:architecture}, only additional operational hardening on top of it.

\section{Validation Methodology Limitations}
\label{sec:discussion_validation_limitations}

Two claims elsewhere in this thesis rest on single-pass evidence rather than systematic measurement, and it is worth stating that distinction plainly rather than leaving it implied. Typed tool schemas (Section~\ref{subsec:impl_csharp_reflection}) guarantee that a call Claude makes is well-formed, a valid tool name with parameters of the right type. They guarantee nothing about whether that call was the right one. Whether Claude selected the correct sub-tool for a given request, or extracted the correct parameter from an anonymised prompt, is a separate question no schema can answer, and no systematic test suite in this thesis answers it either: the worked examples in Chapter~\ref{ch:usecases} show each use case executing correctly once, not routing accuracy measured across a representative set of Italian prompts.

The same gap compounds with a second one. \texttt{AskAntares} calls Claude at temperature 1.0 (Section~\ref{subsec:impl_ask_antares}), a sampling setting under which the same prompt is not guaranteed to produce the same output on repeated calls. A single successful trace, of the kind Chapter~\ref{ch:usecases} presents, says nothing about whether that same prompt would route identically on a second or third attempt. Establishing routing accuracy as a general property of the system, rather than a property observed once per use case, would require running each test prompt multiple times and reporting both the correctness of each run and the consistency across runs, which this thesis did not do.

\section{Moving from Mock Providers to Production Databases}
\label{sec:discussion_production_migration}

Section~\ref{subsec:impl_nswag_migration} already named what remains before Antares AI can run against the real Miorelli tenant: writing \texttt{AntaresMiorelliClient} itself, propagating the caller's real identity instead of the hardcoded fallback in \texttt{IdentityTools}, authentication, role-based access control, and integration testing against the real tenant. Naming those gaps is not the same as ranking them, and the ranking matters for what a team should actually do first.

Identity propagation is the one gap this thesis's own architecture makes structurally hard to defer, not merely inconvenient. Every authorization decision in \texttt{JobTools}, most consequentially Use Case C's three-way authorization gate (Section~\ref{subsec:impl_ucc}), assumes the caller's identity is already known and correct by the time \texttt{ResolveCallerIdentity} runs. Against the mock backend, that assumption is satisfied by a hardcoded fallback, Paolo Ricci, Service Manager, which is safe precisely because nothing behind it is real. Against a real tenant, an incorrect or absent caller identity does not fail loudly; it fails by granting or denying access based on the wrong person's permissions, silently, since the authorization logic itself has no way to distinguish a correctly resolved caller from an incorrectly defaulted one. Authentication and role-based access control are prerequisites to solving this correctly, not separate items that happen to appear on the same list: a real \texttt{AntaresMiorelliClient} fetching real data through an unauthenticated or under-scoped connection would make the authorization gate in \texttt{ReportHolidayRequest} decorative rather than enforced.

Writing \texttt{AntaresMiorelliClient} itself, and the integration testing against it, are comparatively contained by comparison, precisely because the interface it must satisfy, \texttt{IMiorelliService}, was designed and validated first, against the mock (Section~\ref{subsec:impl_miorelli_interface}). The dependency inversion argument made there holds here too: the risk in this migration is concentrated in the identity and access-control layer sitting in front of the interface, not in the interface's own shape, which the internship already spent its validated effort getting right.

\section{Scalability of the Redis Context Mapping}
\label{sec:discussion_redis_scalability}

The current deployment runs a single Redis~\cite{redis2009} instance, reachable only from the Anonymisation Service and the MCP server, holding one key per active anonymisation context. At the request volume this internship's validation exercised, tens of context lookups, this is not a meaningful scalability question: Redis's in-memory architecture, the same property that motivated its selection in Section~\ref{subsec:arch_tokenization_redis}, gives sub-millisecond reads and writes well beyond what a handful of concurrent Antares AI requests would ever demand. The interesting scalability question is not throughput; it is what happens to the key space over time, and that question connects directly to the gap named in Section~\ref{sec:discussion_security_complexity}.

Because context identifiers are freshly generated UUIDs, key collisions between concurrent requests, even from different tenants sharing the same Redis instance, are not a realistic concern; the identifier space is large enough that collision probability is negligible regardless of request volume. What does grow with volume is exactly what Section~\ref{sec:discussion_security_complexity} already identified: without a configured time-to-live, every context not consumed by \texttt{Pop} stays in memory indefinitely. At internship scale this is invisible. At production scale, with a continuous stream of requests and some non-zero rate of errors, abandoned sessions, or client bugs, unconsumed contexts would accumulate without bound, since nothing currently evicts them. This is the same root cause as the persistence gap already discussed, not a separate scalability problem, and the same fix, an explicit time-to-live, addresses both at once: it bounds memory growth and it bounds how long an unconsumed mapping remains a live privacy liability.

A single Redis instance is also a single point of failure, which a production deployment would need to address independently of the time-to-live question, through standard high-availability patterns such as replication with automatic failover or a partitioned cluster deployment. Nothing about the token-map data model described in Section~\ref{subsec:impl_token_reinjection}, a flat, independently-keyed mapping with no cross-context relationships, resists that kind of horizontal scaling. The narrow \texttt{IAnonymizationContextStore} contract every caller depends on would not need to change to sit in front of a clustered deployment instead of a single instance, the same dependency-inversion argument Section~\ref{subsec:impl_miorelli_interface} makes for the Miorelli backend.

\section{Future Extensions}
\label{sec:discussion_future_extensions}

Two extensions were out of scope for this internship but follow naturally from the architecture described in Chapter~\ref{ch:architecture}.

\subsection{Handling Multimodal Inputs (Voice)}
\label{subsec:discussion_voice}

The internship's own training objectives named voice input as a planned second phase, after text-based routing was validated, and nothing in the architecture presented in Chapter~\ref{ch:architecture} rules it out. The privacy boundary this thesis argues for sits at the anonymisation layer, before the LLM, not at the input modality: a voice pipeline would add a speech-to-text transcription step ahead of \texttt{GET /anonymize}, and everything downstream of that endpoint, GLiNER detection, tokenisation, Redis context storage, semantic routing, would be unaffected by where the text came from.

Two properties of the current pipeline would need to hold under spoken rather than typed input, and neither is guaranteed by construction. First, GLiNER's recall on Italian business text (Section~\ref{subsec:usecases_ner_performance}) was measured against clean, hand-typed prompts; transcription errors, disfluencies, and the informality of spoken language would plausibly shift that recall, in an unknown direction, since GLiNER has never been evaluated against transcribed input in this project. Second, PII that spans a transcription error, a misheard digit in a phone number, a name transcribed with the wrong spelling, would not match the mock dataset's known values even if GLiNER correctly identified that \emph{something} PII-shaped was present, which changes the failure mode from a missed detection to a garbled one. Both are measurement questions, not architectural blockers, and both would need their own validation pass before a voice extension could make the same privacy claims Chapter~\ref{ch:usecases} makes for text.

\subsection{Transitioning to Local/On-Premise Models}
\label{subsec:discussion_local_models}

Antares AI currently sends anonymised prompts to Claude over the Anthropic API, an external service, which is exactly the boundary the anonymisation pipeline exists to make safe to cross (Section~\ref{sec:arch_privacy_by_design}). Replacing that external call with a locally hosted model would not remove the need for anonymisation; \texttt{JobTools} still needs Claude's routing decision in anonymised form, and Chapter~\ref{ch:usecases} measured, not assumed, that the current architecture already keeps real PII out of that decision in practice. What a local model would remove is the residual trust placed in a third-party provider's own handling of the payload it does receive, the anonymised prompt and the system prompt, neither of which currently leaves the company's infrastructure in cleartext but both of which are still processed by infrastructure outside the company's control.

The trade-off is not free. Section~\ref{subsec:background_openai_privacy_filter} already noted that a comparable open-weight model exists for the detection layer; routing is a harder substitution, since \texttt{ask\_antares}'s system prompt (Section~\ref{subsec:impl_prompting}) relies on a general-purpose model's instruction-following and tool-use quality, not a narrow, fine-tuned classifier. A locally hosted model capable of the same routing accuracy this thesis measured (Section~\ref{subsec:usecases_ner_performance}) would need to be evaluated against the same test set, not assumed to perform equivalently because it runs on-premise; on-premise execution changes where the computation happens, not whether it is any good at the task.
