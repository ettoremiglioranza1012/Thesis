\chapter{Discussion and Future Work}
\label{ch:discussion}

This chapter reflects on what the implementation and validation described in the previous chapters actually established, and where the current system falls short of what running in production would require. Section~\ref{sec:discussion_security_complexity} weighs the security properties the anonymisation pipeline provides against the architectural complexity it adds, including the prototype-scope gaps already flagged in earlier chapters rather than solved problems. Section~\ref{sec:discussion_validation_limitations} separates what typed schemas and deterministic code actually guarantee from what was measured, and names the routing model's temperature setting as an open methodological question rather than an implicit assumption. Section~\ref{sec:discussion_production_migration} discusses what remains before the mock Miorelli backend can be replaced with the production system. Section~\ref{sec:discussion_redis_scalability} considers how the Redis-based context store would need to change under concurrent, multi-tenant load. Section~\ref{sec:discussion_future_extensions} closes the chapter with two possible extensions: multimodal (voice) input and locally hosted models.

\section{Security vs.\ Complexity Trade-offs}
\label{sec:discussion_security_complexity}

The privacy protections of the anonymisation pipeline fall short of production requirements in two distinct areas. First, the Redis context storing token-to-entity mappings (Section~\ref{subsec:impl_token_reinjection}) lacks a configured time-to-live and any runtime eviction mechanism. Server-side deanonymisation retrieves context via non-destructive reads rather than the intended one-time \texttt{Pop} operation specified in the interface (Section~\ref{subsec:arch_anonymization_service}). Consequently, mappings persist beyond the lifecycle of their originating requests regardless of execution outcome, bounded solely by the lifetime of the host process. This design directly contravenes the storage-limitation principle set forth in Article~5(1)(e) of the GDPR, which mandates that personal data be kept no longer than necessary for its specified purpose~\cite{gdpr2016}.

Second, the per-request reports written to the local \texttt{logs/} directory of \texttt{JobTools} (Section~\ref{sec:impl_jobtools}) present a parallel vulnerability. Although these files remain untransmitted and contain sensitive attributes such as names, phone numbers, and distances, they reside on local disk as unencrypted, unrestricted, and unmanaged artifacts. Standard log-management frameworks classify such data as sensitive by default, requiring encryption, access controls, and strict retention policies rather than indefinite accumulation~\cite{nist2006logmanagement}.

These limitations stem from deliberate scoping decisions established during the development of the prototype. Because the system operates locally as a proof of concept, context persistence is naturally bounded by container lifecycles, and log files remain restricted to the development environment. The primary objective of the internship was to validate the end-to-end functionality of reversible pseudonymisation and MCP-based orchestration rather than to satisfy production-grade security standards. Utilizing non-destructive reads did not impede the validation outcomes detailed in Chapter~\ref{ch:usecases}. Transitioning the system to a production environment requires replacing retrieval calls with the \texttt{Pop} operation, establishing an explicit time-to-live policy within Redis, and enforcing encryption at rest alongside retention rules for local logs, all without modifying the core architecture defined in Chapter~\ref{ch:architecture}.

\section{Validation Methodology Limitations}
\label{sec:discussion_validation_limitations}

Typed tool schemas (Section~\ref{subsec:impl_csharp_reflection}) ensure syntactic correctness by validating tool names and parameter types, yet they offer no assurance regarding semantic appropriateness. Determining whether the model selected the proper sub-tool or correctly extracted parameters from an anonymised prompt falls outside the scope of schema enforcement. Section~\ref{subsec:usecases_ner_performance} addresses this limitation by evaluating routing accuracy directly across 21 hand-built Italian prompts, comprising six per use case and three negative controls. Nevertheless, this evaluation lacks breadth. The test set, authored by a single individual, does not account for external paraphrasing variations, adversarial phrasing designed to disrupt routing, or inputs originating from production environments. Consequently, while schema validity is established, the representativeness of the test suite relative to the broader distribution of real-world Italian requests remains an open question.

A related concern involves model determinism. \texttt{AskAntares} invokes the language model at a temperature of 1.0 (Section~\ref{subsec:impl_ask_antares}), a sampling parameter that precludes output reproducibility across identical prompt executions. To determine whether this setting induces operational variance, Section~\ref{subsec:usecases_ner_performance} subjects each of the 21 test prompts to five repeated trials, yielding 105 total runs. The results demonstrate complete consistency across all repetitions, attributing a single apparent discrepancy in the raw pass rate to an observability artifact rather than routing instability (Table~\ref{tab:routing_summary}). This empirical evidence confirms the absence of observable variance for the evaluated test set at the specified temperature. However, it does not guarantee absolute determinism across the entire input space; prompts positioned near decision boundaries between competing tools could still exhibit variance under identical thermal parameters.

\section{Moving from Mock Providers to Production Databases}
\label{sec:discussion_production_migration}

Transitioning from mock providers to production databases requires addressing several distinct components, though their relative priority dictates the sequence of implementation. Identity propagation represents the most critical impediment, as the current architecture relies on a hardcoded fallback (Paolo Ricci, Service Manager) to satisfy authorization checks such as Use Case C's three-way gate (Section~\ref{subsec:impl_ucc}). In a production environment, an unverified or misconfigured caller identity fails silently by misallocating permissions, bypassing the authorization logic without raising explicit errors. Consequently, authentication and role-based access control~\cite{sandhu1996rbac} must precede production deployment to ensure that downstream authorization mechanisms remain enforceable rather than nominal.

By contrast, implementing \texttt{AntaresMiorelliClient} and conducting corresponding integration tests involve lower structural risk. Because the underlying interface, \texttt{IMiorelliService}, was established and validated against the mock backend (Section~\ref{subsec:impl_miorelli_interface}), the dependency inversion principle ensures that the structural integrity of the interface remains sound. The primary migration risks reside within the access-control layer rather than the interface design itself.

A separate vulnerability exists at the Model Context Protocol (MCP) transport layer. As noted in Section~\ref{sec:background_mcp}, the implementation predates the November 2024 protocol baseline~\cite{mcp2025specnov} and currently accepts connections from any client reaching its port, lacking the OAuth~2.1-based authorization framework introduced in newer specifications. While caller identity management governs permissions within an active session, transport-level authorization controls session initiation. A production deployment requires closing both gaps independently. Adopting the current specification's authorization flow and transitioning the transport layer from HTTP with Server-Sent Events to Streamable HTTP represent self-contained tasks that affect solely the connection management handled by \texttt{ModelContextProtocol.AspNetCore}, leaving business logic and \texttt{JobTools} unaffected.

\section{Scalability of the Redis Context Mapping}
\label{sec:discussion_redis_scalability}

The current deployment utilizes a single Redis~\cite{redis2009} instance restricted to the Anonymisation Service and the MCP server, maintaining one key per active anonymisation context. Under the modest request volumes exercised during the internship, performance is not a bottleneck; Redis in-memory architecture delivers sub-millisecond operations that easily surpass the requirements of concurrent Antares AI requests. The critical scalability concern instead involves key space growth over time, which ties directly to the architectural limitations identified in Section~\ref{sec:discussion_security_complexity}.

Because context identifiers are generated using version~4 UUIDs, key collisions across concurrent requests or multiple tenants sharing the Redis instance are statistically negligible, as the 122 bits of randomness provide an astronomically large identifier space~\cite{ietf2005uuid}. The primary driver of key accumulation is the absence of an explicit time-to-live policy coupled with non-destructive context reads. Without a cleanup mechanism, every mapping remains resident in memory for the duration of the process lifecycle. At production scale, this unbounded accumulation causes continuous memory growth. Resolving this issue requires ensuring that deanonymisation operations consume the retrieved context, supplemented by an explicit time-to-live parameter to bound memory consumption and limit the exposure window of any active mapping.

Addressing single-point-of-failure risks in production requires standard high-availability patterns, such as master-replica replication with automatic failover via Sentinel~\cite{redis2025sentinel} or sharded key distribution across a Redis Cluster deployment~\cite{redis2025cluster}. The flat, independently keyed data model described in Section~\ref{subsec:impl_token_reinjection} requires no modification to accommodate horizontal scaling. The underlying contract of \texttt{IAnonymizationContextStore} insulates callers from infrastructure changes, mirroring the dependency inversion approach applied to the Miorelli backend in Section~\ref{subsec:impl_miorelli_interface}.

\section{Future Extensions}
\label{sec:discussion_future_extensions}

The architectural foundation established in Chapter~\ref{ch:architecture} naturally accommodates future extensions that fell outside the scope of the internship.

\subsection{Handling Multimodal Inputs (Voice)}
\label{subsec:discussion_voice}

Integrating voice input represents a planned second phase following the validation of text-based routing. The privacy boundary enforced by the anonymisation layer remains agnostic to input modality. Introducing a speech-to-text transcription step ahead of the \texttt{GET /anonymize} endpoint allows all downstream components, including GLiNER detection, tokenisation, Redis storage, and semantic routing, to operate without modification.

Deploying this extension requires validating two core assumptions. First, while GLiNER recall was evaluated against clean Italian text in Section~\ref{subsec:usecases_ner_performance}, spoken language introduces transcription errors, disfluencies, and informality that could unpredictably impact performance. Furthermore, named entities are notoriously difficult for automatic speech recognition (ASR) systems to transcribe accurately due to vocabulary biases~\cite{mao2020underrepresented}, and traditional word-error-rate metrics correlate poorly with downstream named-entity recognition degradation~\cite{jannet2015asrner}. Second, transcription inaccuracies within personally identifiable information, such as misheard digits or misspelled names, prevent matches against the mock dataset, shifting failure modes from missed detections to garbled identifiers. Empirical validation is therefore necessary before extending privacy guarantees to voice data.

\subsection{Transitioning to Local/On-Premise Models}
\label{subsec:discussion_local_models}

Antares AI currently routes anonymised prompts through the external Anthropic API, a boundary secured by the anonymisation pipeline (Section~\ref{sec:arch_privacy_by_design}). Substituting this external service with a locally hosted model eliminates reliance on third-party infrastructure for payload processing, although the anonymisation layer remains necessary to protect sensitive data.

This transition involves distinct engineering trade-offs. While open-weight alternatives exist for named entity recognition (Section~\ref{subsec:background_openai_privacy_filter}), semantic routing relies on advanced instruction-following and tool-use capabilities. Standardised function-calling benchmarks demonstrate significant performance variations among open models of comparable size~\cite{patil2025bfcl}, necessitating direct empirical evaluation rather than assuming parity with proprietary APIs. Any candidate local model must be assessed against the established test suite (Section~\ref{subsec:usecases_ner_performance}) to ensure it matches the required routing accuracy.
