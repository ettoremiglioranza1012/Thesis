\chapter{Discussion and Future Work}
\label{ch:discussion}

This chapter reflects on what the implementation and validation described in the previous chapters actually established, and where the current system falls short of what running in production would require. Section~\ref{sec:discussion_security_complexity} weighs the security properties the anonymisation pipeline provides against the architectural complexity it adds, including the prototype-scope gaps already flagged in earlier chapters rather than solved problems. Section~\ref{sec:discussion_validation_limitations} separates what typed schemas and deterministic code actually guarantee from what was measured, and names the routing model's temperature setting as an open methodological question rather than an implicit assumption. Section~\ref{sec:discussion_production_migration} discusses what remains before the mock Miorelli backend can be replaced with the production system. Section~\ref{sec:discussion_redis_scalability} considers how the Redis-based context store would need to change under concurrent, multi-tenant load. Section~\ref{sec:discussion_future_extensions} closes the chapter with two possible extensions: multimodal (voice) input and locally hosted models.

\section{Security vs.\ Complexity Trade-offs}
\label{sec:discussion_security_complexity}

The anonymisation pipeline's privacy protections stop short of what a production deployment would require in two related places. The Redis context holding token-to-entity mappings (Section~\ref{subsec:impl_token_reinjection}) has no time-to-live configured, and, more significantly, nothing in the current implementation ever removes a mapping while the process is running: server-side deanonymisation reads the context non-destructively rather than through the one-time-use \texttt{Pop} operation the interface declares for exactly this purpose (Section~\ref{subsec:arch_anonymization_service}), so a mapping outlives the request it was created for regardless of whether that request succeeds, fails, or is abandoned mid-flow. In this prototype the gap is bounded only by the process's own lifetime, since nothing else evicts a context. The GDPR names this precise failure mode directly: Article~5(1)(e) requires personal data to be kept no longer than necessary for the purpose it was collected for, a storage-limitation obligation that applies to a token-map mapping the same way it applies to any other record of personal data~\cite{gdpr2016}. The per-request reports written to \texttt{JobTools}'s local \texttt{logs/} directory (Section~\ref{sec:impl_jobtools}) sit on the other side of the same gap: they contain real names, phone numbers, and distances, are never transmitted anywhere and were never intended to be, but they are also an unencrypted, access-uncontrolled, retention-unmanaged record on local disk, exactly the class of asset standard log-management guidance treats as sensitive by default and recommends protecting with access controls, encryption, and a defined retention period, not leaving it to accumulate indefinitely on whatever disk the process happens to run on~\cite{nist2006logmanagement}.

Neither gap was addressed during the internship, but they are not the same kind of gap. The absent time-to-live and the missing persistence volume are deliberate scope decisions: the system runs as a local proof of concept, every context is cleared the moment the container stops regardless of what happened to individual mappings before that, and the log files exist on a machine no one outside the development team has access to. That server-side deanonymisation reads a context through \texttt{Get} instead of consuming it through the \texttt{Pop} operation the interface was built around is a different kind of gap: nothing in the project record states this as intentional, and its effect is that a mapping is never removed by the application on any path, not only on the error paths a working one-time-use design would still have left exposed. What the internship needed to show was that reversible pseudonymisation and its MCP-based orchestration work correctly end to end, not that the system already meets the retention and access-control standards a production deployment would be held to; on that narrower goal, using \texttt{Get} throughout did not stop the validation in Chapter~\ref{ch:usecases} from passing. It did not need one-time-use semantics to produce correct results on the cases tested. Closing this gap for a production deployment would mean making \texttt{Pop} the call \texttt{/deanonymize-known} actually uses, configuring an explicit time-to-live on the Redis context as a backstop, and defining a retention and deletion policy for the log files, encrypting them at rest; none of this requires redesigning the architecture described in Chapter~\ref{ch:architecture}, only fixing and hardening what already exists.

\section{Validation Methodology Limitations}
\label{sec:discussion_validation_limitations}

Typed tool schemas (Section~\ref{subsec:impl_csharp_reflection}) guarantee that a call Claude makes is well-formed, a valid tool name with parameters of the right type. They guarantee nothing about whether that call was the right one. Whether Claude selected the correct sub-tool for a given request, or extracted the correct parameter from an anonymised prompt, is a separate question no schema can answer, and Chapter~\ref{ch:usecases} does not leave it unanswered: Section~\ref{subsec:usecases_ner_performance} runs 21 hand-built Italian prompts, six per use case plus three negative controls, and measures routing accuracy directly rather than inferring it from schema conformance. What that measurement does not cover is breadth. Twenty-one prompts, written by one person to exercise each use case's intended path, say nothing about paraphrasing this specific dataset did not happen to include, adversarial phrasing designed to confuse the router, or prompts drawn from an actual deployment rather than constructed for a test set. Schema validity was never the open question; representativeness of the 21-prompt set against the full space of real Italian requests still is.

The same test also addresses a second, related gap. \texttt{AskAntares} calls Claude at temperature 1.0 (Section~\ref{subsec:impl_ask_antares}), a sampling setting under which the same prompt is not guaranteed to produce the same output on repeated calls, so a single successful trace would say nothing about whether that same prompt routes identically on a second or third attempt. Section~\ref{subsec:usecases_ner_performance} runs each of the 21 prompts five times, 105 trials in total, and finds all 21 fully consistent across every repetition, with the one apparent discrepancy in the raw pass rate traced to an observability blind spot in the detection method rather than to the router itself (Table~\ref{tab:routing_summary}). That result answers the specific methodological question this component was built to settle, whether temperature 1.0 produces observable run-to-run routing variance on this test set, and it did not. It does not establish that no prompt at that temperature would ever vary; it establishes that none of these 21 did, across five attempts each. A prompt sitting closer to the decision boundary between two tools, one this hand-built set did not happen to construct, remains an open case temperature 1.0 could still affect.

\section{Moving from Mock Providers to Production Databases}
\label{sec:discussion_production_migration}

Section~\ref{subsec:impl_nswag_migration} already named what remains before Antares AI can run against the real Miorelli tenant: writing \texttt{AntaresMiorelliClient} itself, propagating the caller's real identity instead of the hardcoded fallback in \texttt{IdentityTools}, authentication, role-based access control, and integration testing against the real tenant. Naming those gaps is not the same as ranking them, and the ranking matters for what a team should actually do first.

Identity propagation is the one gap this thesis's own architecture makes structurally hard to defer, not merely inconvenient. Every authorization decision in \texttt{JobTools}, most consequentially Use Case C's three-way authorization gate (Section~\ref{subsec:impl_ucc}), assumes the caller's identity is already known and correct by the time \texttt{ResolveCallerIdentity} runs. Against the mock backend, that assumption is satisfied by a hardcoded fallback, Paolo Ricci, Service Manager, which is safe precisely because nothing behind it is real. Against a real tenant, an incorrect or absent caller identity does not fail loudly; it fails by granting or denying access based on the wrong person's permissions, silently, since the authorization logic itself has no way to distinguish a correctly resolved caller from an incorrectly defaulted one. Authentication and role-based access control~\cite{sandhu1996rbac} are prerequisites to solving this correctly: a real \texttt{AntaresMiorelliClient} fetching real data through an unauthenticated or under-scoped connection would make the authorization gate in \texttt{ReportHolidayRequest} decorative rather than enforced.

Writing \texttt{AntaresMiorelliClient} itself, and the integration testing against it, are comparatively contained by comparison, precisely because the interface it must satisfy, \texttt{IMiorelliService}, was designed and validated first, against the mock (Section~\ref{subsec:impl_miorelli_interface}). The dependency inversion argument made there holds here too: the risk in this migration is concentrated in the identity and access-control layer sitting in front of the interface, not in the interface's own shape, which the internship already spent its validated effort getting right.

A related but separate gap sits one layer up, at the MCP transport itself rather than at the Miorelli backend. Section~\ref{sec:background_mcp} noted that the specification has moved on since the November 2024 baseline this server was built against~\cite{mcp2025specnov}: an OAuth~2.1-based authorization framework now exists for authenticating the connection between an MCP client and an MCP server, and this implementation predates it, so the MCP server accepts a connection from any client that can reach its port. That is a different problem from the caller-identity gap discussed above; it is about who is allowed to open an MCP session at all, not about whose permissions apply once one is open, but a real deployment would need to close both before either the identity propagation fix or the authorization framework added here means very much on its own. Adopting the current specification's authorization flow, and moving the transport from HTTP with Server-Sent Events to Streamable HTTP as the same revision also requires, is additional, self-contained work: neither change touches \texttt{JobTools} or any business logic, since both operate at the connection layer \texttt{ModelContextProtocol.AspNetCore} already owns.

\section{Scalability of the Redis Context Mapping}
\label{sec:discussion_redis_scalability}

The current deployment runs a single Redis~\cite{redis2009} instance, reachable only from the Anonymisation Service and the MCP server, holding one key per active anonymisation context. At the request volume this internship's validation exercised, tens of context lookups, this is not a meaningful scalability question: Redis's in-memory architecture, the same property that motivated its selection in Section~\ref{subsec:arch_tokenization_redis}, gives sub-millisecond reads and writes well beyond what a handful of concurrent Antares AI requests would ever demand. The interesting scalability question here is what happens to the key space over time, not throughput, and it connects directly to the gap named in Section~\ref{sec:discussion_security_complexity}.

Because context identifiers are freshly generated UUIDs, key collisions between concurrent requests, even from different tenants sharing the same Redis instance, are not a realistic concern; the standard defining the random (version~4) UUID format used here reserves 122 bits for randomness, making the identifier space large enough that collision probability is negligible regardless of any request volume this system could plausibly reach~\cite{ietf2005uuid}. What does grow with volume is exactly what Section~\ref{sec:discussion_security_complexity} already identified: without a configured time-to-live, and with deanonymisation never actually removing a context, every mapping written to Redis stays in memory for as long as the process runs, not only the ones tied to a request that never completed. At internship scale this is invisible. At production scale, with a continuous stream of requests, contexts would accumulate without bound regardless of how many requests succeed, since nothing currently evicts any of them. This is the same root cause as the persistence gap already discussed, not a separate scalability problem, and the same fix addresses both at once: making deanonymisation actually consume the context it reads, with an explicit time-to-live as a backstop, bounds memory growth and bounds how long any one mapping remains a live privacy liability.

A single Redis instance is also a single point of failure, which a production deployment would need to address independently of the time-to-live question, through standard high-availability patterns such as replication with automatic failover or a partitioned cluster deployment~\cite{kleppmann2017ddia}. Redis ships both of these as first-class deployment modes rather than requiring them to be built externally: Sentinel monitors a primary/replica set and promotes a replica automatically on failure~\cite{redis2025sentinel}, and Cluster shards the key space across multiple nodes so no single instance holds the whole dataset~\cite{redis2025cluster}. Nothing about the token-map data model described in Section~\ref{subsec:impl_token_reinjection}, a flat, independently-keyed mapping with no cross-context relationships, resists that kind of horizontal scaling. The narrow \texttt{IAnonymizationContextStore} contract every caller depends on would not need to change to sit in front of a clustered deployment instead of a single instance, the same dependency-inversion argument Section~\ref{subsec:impl_miorelli_interface} makes for the Miorelli backend.

\section{Future Extensions}
\label{sec:discussion_future_extensions}

Two extensions were out of scope for this internship but follow naturally from the architecture described in Chapter~\ref{ch:architecture}.

\subsection{Handling Multimodal Inputs (Voice)}
\label{subsec:discussion_voice}

The internship's own training objectives named voice input as a planned second phase, after text-based routing was validated, and nothing in the architecture presented in Chapter~\ref{ch:architecture} rules it out. The privacy boundary this thesis argues for sits at the anonymisation layer, before the LLM, not at the input modality: a voice pipeline would add a speech-to-text transcription step ahead of \texttt{GET /anonymize}, and everything downstream of that endpoint, GLiNER detection, tokenisation, Redis context storage, semantic routing, would be unaffected by where the text came from.

Two properties of the current pipeline would need to hold under spoken rather than typed input, and neither is guaranteed by construction. First, GLiNER's recall on Italian business text (Section~\ref{subsec:usecases_ner_performance}) was measured against clean, hand-typed prompts; transcription errors, disfluencies, and the informality of spoken language would plausibly shift that recall, in an unknown direction, since GLiNER has never been evaluated against transcribed input in this project. Named entities are also disproportionately hard for ASR systems to transcribe correctly in the first place, being underrepresented relative to common vocabulary in the data these systems are trained on~\cite{mao2020underrepresented}, and standard word-error-rate scoring is known to correlate poorly with how much an ASR system's mistakes actually damage downstream named-entity recognition~\cite{jannet2015asrner}, which is the property a voice extension to this pipeline would actually depend on. Second, PII that spans a transcription error, a misheard digit in a phone number, a name transcribed with the wrong spelling, would not match the mock dataset's known values even if GLiNER correctly identified that \emph{something} PII-shaped was present, which changes the failure mode from a missed detection to a garbled one. Both are measurement questions, not architectural blockers, and both would need their own validation pass before a voice extension could make the same privacy claims Chapter~\ref{ch:usecases} makes for text.

\subsection{Transitioning to Local/On-Premise Models}
\label{subsec:discussion_local_models}

Antares AI currently sends anonymised prompts to Claude over the Anthropic API, an external service, which is exactly the boundary the anonymisation pipeline exists to make safe to cross (Section~\ref{sec:arch_privacy_by_design}). Replacing that external call with a locally hosted model would not remove the need for anonymisation; \texttt{JobTools} still needs Claude's routing decision in anonymised form, and Chapter~\ref{ch:usecases} measured, not assumed, that the current architecture already keeps real PII out of that decision in practice. What a local model would remove is the residual trust placed in a third-party provider's own handling of the payload it does receive, the anonymised prompt and the system prompt, neither of which currently leaves the company's infrastructure in cleartext but both of which are still processed by infrastructure outside the company's control.

The trade-off is not free. Section~\ref{subsec:background_openai_privacy_filter} already noted that a comparable open-weight model exists for the detection layer; routing is a harder substitution, since \texttt{ask\_antares}'s system prompt (Section~\ref{subsec:impl_prompting}) relies on a general-purpose model's instruction-following and tool-use quality, not a narrow, fine-tuned classifier. Standardised function-calling evaluation exists for exactly this comparison: benchmarks that score models on selecting and correctly parameterising a tool call, independent of any specific deployment, show meaningful variation in tool-use quality across models of comparable size and openness~\cite{patil2025bfcl}, which is a reason to measure a candidate local model directly rather than assume open-weight and general-purpose imply comparable routing quality. A locally hosted model capable of the same routing accuracy this thesis measured (Section~\ref{subsec:usecases_ner_performance}) would need to be evaluated against the same test set, not assumed to perform equivalently because it runs on-premise; on-premise execution changes where the computation happens, not whether it is any good at the task.
