\chapter{Use Cases and Validation}
\label{ch:usecases}

Chapters~\ref{ch:architecture} and~\ref{ch:implementation} described the architecture and the implementation of Antares AI's three business use cases. This chapter validates them, against a fixed mock dataset and a purpose-built evaluation harness that exercises the running system through its real interfaces rather than its internal code paths. Section~\ref{sec:usecases_domain_overview} summarises the workforce management domain the three use cases operate on. Section~\ref{sec:usecases_spatial_querying}, Section~\ref{sec:usecases_colleague_identification}, and Section~\ref{sec:usecases_holiday_request} report end-to-end correctness for Use Cases A, B, and C respectively, against an independent reference implementation built separately from the system under test. Section~\ref{sec:usecases_validation} closes the chapter with the two cross-cutting quantitative results the privacy and correctness claims of the previous chapters were left resting on: how often PII detection fails, whether that failure ever reaches the LLM payload, and how consistently the routing model selects the correct tool under its configured sampling temperature.

% ==========================================
\section{Workforce Management Domain Overview}
\label{sec:usecases_domain_overview}

Section~\ref{sec:arch_antares_ecosystem} already introduced the Antares/Miorelli domain: \emph{persone}, \emph{cantieri}, and \emph{ticket} as the three core entity types, and the \texttt{PULITO\_DA}, \texttt{RESPONSABILE\_DI\_RIFERIMENTO}, and \texttt{AUTORIZZATORE} relations that structure the three use cases this chapter validates. This section does not repeat that description; it fixes the concrete dataset and scope every result below was measured against.

Every use case validated in this chapter runs against \texttt{MiorelliMockDataProvider.cs}: ten persons, three cantieri (Bergamo, Brescia, Mantova), the \texttt{PULITO\_DA} work assignments linking persons to cantieri, and five absence tickets, all dated within 2026-03-28 to 2026-04-10. No production Miorelli backend and no real employee data were touched at any point in this validation; every number in this chapter was produced against this fixed, fictional dataset, consistent with the prototype scope stated in Section~\ref{sec:impl_backend_integration}.

\subsection{Haversine Distance and Radius Filtering}
\label{subsec:usecases_haversine}

Each test case is checked against an independently computed expected result, not against the system's own output re-derived from its own logic. The reference used for this comparison is a hand-built mirror of the mock dataset with its own Haversine implementation, written separately from \texttt{PersonTools.CalculateDistanceAndRank} (Section~\ref{subsec:impl_uca}) and sharing no code with it. \subsection{Execution Flow and Prompt Handling}
\label{subsec:usecases_spatial_flow}

\texttt{ask\_antares} returns only free text to its caller; it does not itself expose which sub-tool ran. What does expose it, without any change to server code, is the report file each \texttt{JobTools} invocation already writes to \texttt{logs/} (Section~\ref{sec:impl_jobtools}): a use-case-tagged, timestamped file whose name identifies which of the three tools actually executed. The validation harness snapshots that directory before and after each \texttt{ask\_antares} call and identifies the new file by name, giving a reliable, zero-instrumentation way to observe routing decisions from outside the system. Section~\ref{subsec:usecases_ner_performance} reports the routing accuracy and consistency results this technique produced, for all three use cases together, since the same methodology and the same headline numbers apply across UC-A, UC-B, and UC-C.

\section{Privacy and Functional Validation}
\label{sec:usecases_validation}

The preceding three sections validated business-logic correctness. This section validates the two claims Chapters~\ref{ch:architecture} and~\ref{ch:implementation} left open pending measurement: whether PII actually reaches the LLM payload in practice, and how accurately and consistently the routing model selects the correct tool given its configured sampling temperature. Both were measured against the running system through its real interfaces, not against its internal code paths, over a fifty-prompt Italian test set built for this purpose.

\subsection{Auditing the LLM Context Boundary}
\label{subsec:usecases_llm_audit}

Section~\ref{sec:arch_privacy_by_design} states the structural claim directly: PII isolation holds only for entities the detection layer actually finds. This section reports the measurement behind that claim: how often GLiNER misses a real PII entity, and whether a missed entity actually reaches Claude's context.

\texttt{AntaresTools.AskAntares} sends Claude exactly two messages per call: a static Italian system prompt, unchanged except for the \texttt{context\_id} it carries, and a user message equal to whatever \texttt{user\_input} string the caller supplied. Because the validation harness is that caller, it constructs \texttt{user\_input} itself, which makes the exact literal payload Claude receives fully reconstructable client-side, with no server-side logging, instrumentation, or code change of any kind. That reconstructed payload was scanned, for all fifty test prompts, for any of thirty-nine known real PII values drawn from the mock dataset: full names, phone numbers, email addresses, and full site or company descriptors.

Two leaks were found, out of fifty prompts scanned: an email address in one prompt and a different email address in another, both cases where GLiNER failed to tag the address in its specific sentence context. Both leaks correlate with a GLiNER false negative reported in Section~\ref{subsec:usecases_ner_performance}; no leak was found that did not correlate with a detection miss. This supports the structural claim in Section~\ref{sec:arch_privacy_by_design}: the anonymisation layer has no independent bypass path, and the privacy guarantee this architecture provides reduces to detection recall. Each entry in the false-negative list below is therefore a specific, confirmed PII leak path, not only a statement about NER quality.

\subsection{Routing Accuracy and NER Performance in Italian}
\label{subsec:usecases_ner_performance}

\textbf{PII detection.} Fifty hand-built Italian prompts, carrying eighty-two labelled entity spans, were evaluated against the live \texttt{/anonymize} endpoint at its production configuration (Section~\ref{subsec:impl_gliner_pivot}): the real GLiNER-based detection path, threshold 0.45, the full eight-label set. Two metrics are reported: \emph{coverage}, whether a PII substring was tokenised at all regardless of the label predicted for it, which is the property that actually determines whether PII can leak; and \emph{strict}, standard span-and-label NER evaluation. Table~\ref{tab:gliner_metrics} reports both metrics in full.

\begin{table}[htbp]
\centering
\caption{GLiNER PII detection results (50 prompts, 82 labelled entity spans)}
\label{tab:gliner_metrics}
\begin{tabular}{lrrrrrr}
\hline
\textbf{Metric} & \textbf{TP} & \textbf{FP} & \textbf{FN} & \textbf{Precision} & \textbf{Recall} & \textbf{F1} \\
\hline
Coverage & 75 & 5 & 7 & 0.938 & 0.915 & 0.926 \\

Seven entities were missed entirely under the coverage metric, itemized in Table~\ref{tab:gliner_fn}. Two were email addresses missed mid-sentence, both already identified in Section~\ref{subsec:usecases_llm_audit} as the two payload leaks, marked accordingly in the table. Four were Italian date-range expressions of the form \emph{``dal~X~al~Y~[aprile]''}, and one was a bare cantiere-city reference embedded inside a compound site descriptor. The date-range pattern accounts for four of the seven false negatives, the largest recurring failure mode in this test set: at its current threshold and label configuration, GLiNER's weakness on this test set is specific to Italian date-range phrasing, not PII detection generally.

Five false positives were also observed, none of them random noise: two are generic temporal expressions plausibly mislabelled under a recall-favouring threshold, two are bare city or region names used generically inside a prompt built specifically to probe that behaviour, and one is a genuine spurious organisation detection. The gap between strict recall (0.829) and coverage recall (0.915) is consistent with the design rationale already stated in Section~\ref{subsec:impl_gliner_pivot}: the 0.45 threshold catches more entities than it assigns correct labels to, which is the expected shape of a configuration deliberately tuned toward recall over precision.

\textbf{Routing accuracy and temperature consistency.} Twenty-one prompts, six per use case plus three out-of-scope negative controls, were each run five times through the full anonymise-then-route pipeline, since the routing model runs at temperature 1.0 (Section~\ref{subsec:impl_ask_antares}) and a single pass cannot establish whether that setting produces run-to-run variation. Table~\ref{tab:routing_summary} reports the aggregate results: on this test set, temperature 1.0 produced no observed run-to-run routing variance.

\begin{table}[htbp]
\centering
\caption{Routing accuracy and consistency (21 prompts, N=5 repetitions, 105 trials)}
\label{tab:routing_summary}
\begin{tabular}{lr}
\hline
\textbf{Metric} & \textbf{Value} \\
\hline
Measured accuracy (log-diffing method) & 95.2\% (100/105) \\
True accuracy (adjusted, see below) & $\sim$100\% (105/105) \\
Prompts fully consistent across all 5 reps & 21/21 \\
\hline
\end{tabular}

One prompt, requesting a holiday ticket for a person with no \texttt{PULITO\_DA} cantiere assignment in the mock dataset, registered as zero correct out of five trials under the log-diffing detection method described in Section~\ref{subsec:usecases_spatial_flow}. The response text shows Claude selected \texttt{report\_holiday\_request} correctly on all five repetitions; the tool returned a legitimate business-logic failure message, since that person has no eligible cantiere, and exited before writing the log file the log-diffing method relies on. True routing accuracy on this dataset is therefore 105 of 105; the 95.2\% in Table~\ref{tab:routing_summary} reflects a limitation of the log-diffing method, not a routing error.

The same routing data also shows, for the canonical UC-A prompt, that Claude invoked \texttt{get\_nearest\_workers\_to\_cantiere} three times within a single \texttt{ask\_antares} call, once per GLiNER's three fragmented location tokens (Section~\ref{subsec:arch_tokenization_redis}), instead of treating them as one compound site descriptor. All three calls resolve to the same cantiere, and the end-to-end result in Section~\ref{sec:usecases_spatial_querying} is correct, but the behaviour generalises beyond this case: fragmented anonymisation can change how many times, and with what parameters, the model invokes a business tool, and a differently fragmented prompt could produce more than one genuinely incorrect lookup instead of three redundant correct ones.
