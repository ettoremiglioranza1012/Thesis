\chapter{Use Cases and Validation}
\label{ch:usecases}

Chapters~\ref{ch:architecture} and~\ref{ch:implementation} described the architecture and the implementation of Antares AI's three business use cases. This chapter validates them, against a fixed mock dataset and a purpose-built evaluation harness that exercises the running system through its real interfaces rather than its internal code paths. Section~\ref{sec:usecases_domain_overview} summarises the workforce management domain the three use cases operate on. Section~\ref{sec:usecases_spatial_querying}, Section~\ref{sec:usecases_colleague_identification}, and Section~\ref{sec:usecases_holiday_request} report end-to-end correctness for Use Cases A, B, and C respectively, against an independent reference implementation built separately from the system under test. Section~\ref{sec:usecases_validation} closes the chapter with the two cross-cutting quantitative results the privacy and correctness claims of the previous chapters were left resting on, how often PII detection fails and whether that failure ever reaches the LLM payload, how consistently the routing model selects the correct tool under its configured sampling temperature, and ends by mapping each result back to the three research questions posed in Section~\ref{sec:intro_objectives}, stating plainly what is answered and what is not.

\section{Workforce Management Domain Overview}
\label{sec:usecases_domain_overview}

Section~\ref{sec:arch_antares_ecosystem} already introduced the Antares/Miorelli domain: \emph{persone}, \emph{cantieri}, and \emph{ticket} as the three core entity types, and the \texttt{PULITO\_DA}, \texttt{RESPONSABILE\_DI\_RIFERIMENTO}, and \texttt{AUTORIZZATORE} relations that structure the three use cases this chapter validates. This section does not repeat that description; it fixes the concrete dataset and scope every result below was measured against.

Every use case validated in this chapter runs against \texttt{MiorelliMockDataProvider.cs}: ten persons, three cantieri (Bergamo, Brescia, Mantova), the \texttt{PULITO\_DA} work assignments linking persons to cantieri, and five absence tickets, all dated within 2026-03-28 to 2026-04-10. No production Miorelli backend and no real employee data were touched at any point in this validation; every number in this chapter was produced against this fixed, fictional dataset, consistent with the prototype scope stated in Section~\ref{sec:impl_backend_integration}.

\section{Use Case A: Spatial Querying for Construction Sites}
\label{sec:usecases_spatial_querying}

Use Case A is validated against four test cases exercising \texttt{get\_nearest\_workers\_to\_cantiere}: the canonical Bergamo prompt already traced in Section~\ref{subsec:arch_tokenization_redis}, one case each for the other two cantieri, and one case naming a cantiere that does not exist, to exercise the not-found path.

\subsection{Haversine Distance and Radius Filtering}
\label{subsec:usecases_haversine}

Each test case is checked against an independently computed expected result, not against the system's own output re-derived from its own logic, the standard response to the test oracle problem: a test that checks a system's output against a value the same system also produced cannot detect a fault shared by both computations~\cite{barr2015oracle}. Comparing two independently written implementations against each other, rather than checking one implementation's output against a fixed expected value, is itself a named technique, differential testing, on the premise that two programs solving the same problem from different code are unlikely to share the same bug~\cite{mckeeman1998differential}. The reference used for this comparison is a hand-built mirror of the mock dataset with its own Haversine implementation, written separately from \texttt{PersonTools.CalculateDistanceAndRank} (Section~\ref{subsec:impl_uca}) and sharing no code with it. Before running the full test set, the formula itself was spot-checked against a live server report: for the canonical Bergamo prompt at a 15\,km radius, the server logged two workers at 0.9\,km and 1.9\,km respectively, and the independent calculation matched both distances to within 0.1\,km.

Table~\ref{tab:uca_e2e} summarises all four cases. Every case matched the independent reference on every repetition. The Mantova case reports no matches because both assigned workers live outside the 15\,km radius, which the independent reference confirms is the correct result.

\subsection{Execution Flow and Prompt Handling}
\label{subsec:usecases_spatial_flow}

\texttt{ask\_antares} returns only free text to its caller; it does not itself expose which sub-tool ran. What does expose it, without any change to server code, is the report file each \texttt{JobTools} invocation already writes to \texttt{logs/} (Section~\ref{sec:impl_jobtools}): a use-case-tagged, timestamped file whose name identifies which of the three tools actually executed. The validation harness snapshots that directory before and after each \texttt{ask\_antares} call and identifies the new file by name, giving a reliable, zero-instrumentation way to observe routing decisions from outside the system. Section~\ref{subsec:usecases_ner_performance} reports the routing accuracy and consistency results this technique produced, for all three use cases together, since the same methodology and the same headline numbers apply across UC-A, UC-B, and UC-C.

\section{Privacy and Functional Validation}
\label{sec:usecases_validation}

The preceding three sections validated business-logic correctness. This section validates the two claims Chapters~\ref{ch:architecture} and~\ref{ch:implementation} left open pending measurement: whether PII actually reaches the LLM payload in practice, and how accurately and consistently the routing model selects the correct tool given its configured sampling temperature. Both were measured against the running system through its real interfaces, not against its internal code paths, over a fifty-prompt Italian test set built for this purpose.

\subsection{Auditing the LLM Context Boundary}
\label{subsec:usecases_llm_audit}

Section~\ref{sec:arch_privacy_by_design} states the structural claim directly: PII isolation holds only for entities the detection layer actually finds. This section reports the measurement behind that claim: how often GLiNER misses a real PII entity, and whether a missed entity actually reaches Claude's context.

\texttt{AntaresTools.AskAntares} sends Claude exactly two messages per call: a static Italian system prompt, unchanged except for the \texttt{context\_id} it carries, and a user message equal to whatever \texttt{user\_input} string the caller supplied. Because the validation harness is that caller, it constructs \texttt{user\_input} itself, which makes the exact literal payload Claude receives fully reconstructable client-side, with no server-side logging, instrumentation, or code change of any kind. That reconstructed payload was scanned, for all fifty test prompts, for any of thirty-nine known real PII values drawn from the mock dataset: full names, phone numbers, email addresses, and full site or company descriptors.

Two leaks were found, out of fifty prompts scanned: an email address in one prompt and a different email address in another, both cases where GLiNER failed to tag the address in its specific sentence context. Both leaks correlate with a GLiNER false negative reported in Section~\ref{subsec:usecases_ner_performance}; no leak was found that did not correlate with a detection miss. This supports the structural claim in Section~\ref{sec:arch_privacy_by_design}: the anonymisation layer has no independent bypass path, and the privacy guarantee this architecture provides reduces to detection recall. Each entry in the false-negative list below is therefore a specific, confirmed PII leak path, not only a statement about NER quality.

\subsection{Routing Accuracy and NER Performance in Italian}
\label{subsec:usecases_ner_performance}

\textbf{PII detection.} Fifty hand-built Italian prompts, carrying eighty-two labelled entity spans, were evaluated against the live \texttt{/anonymize} endpoint at its production configuration (Section~\ref{subsec:impl_gliner_pivot}): the real GLiNER-based detection path, threshold 0.45, the full eight-label set. Two metrics are reported: \emph{coverage}, whether a PII substring was tokenised at all regardless of the label predicted for it, which is the property that actually determines whether PII can leak; and \emph{strict}, standard span-and-label NER evaluation in the sense established by the CoNLL-2003 shared task~\cite{tjongkimsang2003conll}. The coverage/strict split itself follows an older evaluation precedent: the MUC-6 shared task scored NER systems under both an exact match and a relaxed match that credited a correct span even when the predicted label was wrong, precisely because the two errors have different downstream consequences and collapsing them into one number hides which kind of mistake a system is actually making~\cite{sundheim1995muc6}. Here that distinction is what separates a privacy failure (coverage) from a merely mislabelled but still-masked entity (strict). Table~\ref{tab:gliner_metrics} reports both metrics in full.

Seven entities were missed entirely under the coverage metric, itemized in Table~\ref{tab:gliner_fn}. Two were email addresses missed mid-sentence, both already identified in Section~\ref{subsec:usecases_llm_audit} as the two payload leaks, marked accordingly in the table. Four share a single pattern: Italian date-range expressions of the form \emph{``dal~X~al~Y~[aprile]''}. The seventh, a bare cantiere-city reference (\emph{Brescia}) embedded inside a longer compound site descriptor, does not fit that pattern and is treated separately below.

Calling the date-range misses an Italian-language weakness is not precise enough to be useful, and the four instances in Table~\ref{tab:gliner_fn} support a narrower, checkable explanation instead. A range expression like \emph{``dal 3 al 7 aprile''} names two numeric endpoints and one shared month across a five-token span, joined by two prepositions rather than by adjacency. A single date, \emph{``il 3 aprile''} or \emph{``il 07/04/2026''}, is a contiguous, self-contained span of the kind GLiNER's zero-shot conditioning is built to recognise from a short label description. The label set the Anonymisation Service actually requests (Section~\ref{subsec:impl_gliner_pivot}) offers only a bare \texttt{"date"} label; nothing in that description tells the model that two dates joined by \emph{dal}/\emph{al} should be scored as one entity rather than as two separate, weaker date mentions, or as no entity at all if neither half looks like a complete date on its own. Table~\ref{tab:gliner_metrics}'s five false positives include two temporal expressions the model did flag, which argues against a general blindness to Italian date phrasing and toward a narrower cause: single dates and generic temporal phrases score highly enough to pass threshold, five-token range constructions built from two of them do not. This is stated as the most likely explanation given the data available here, not as a confirmed root cause; testing it directly would mean adding an explicit \texttt{"date range"} or \texttt{"periodo"} label at inference time and re-running this same test set, which this thesis did not do. The broader pattern this hypothesis points at, a span-based model under-performing on an entity that is naturally composed of multiple linked pieces rather than one contiguous mention, has independent precedent in NER work on discontinuous entities, where the standard contiguous-span decoding assumption is itself identified as the source of the difficulty~\cite{dai2020discontinuous}. A date range is not discontinuous in the strict sense that literature targets, its tokens are contiguous in the sentence, but the underlying difficulty is structurally related: the entity's boundaries do not coincide with what a single-span, single-label decision was designed to capture. Absence-period phrasing of exactly this shape is what a real Use Case~C holiday request names (Section~\ref{sec:usecases_holiday_request}), which is reason enough to run that test: a missed date range in that context is not a hypothetical risk. It is the same failure mode this test set already measured, on the same kind of sentence UC-C is built to handle.

The seventh miss, \emph{Brescia}, is a different kind of failure and should not be folded into the date-range explanation above. Prompt B4 names the cantiere as \emph{``Brescia Via Risorgimento 8''}; GLiNER tokenised \emph{Via Risorgimento 8} as \texttt{<LOCATION\_0001>} but left the leading city name untouched. Table~\ref{tab:gliner_metrics}'s false positives include the opposite error on a different prompt (C5): \emph{Bergamo} flagged as a location when the sentence is explicitly contrasting the city from the cantiere named after it. Read together, these two results do not show GLiNER failing on city names as a category; they show the model's decision on a bare city name swinging on sentence-level context in a way a single confidence threshold cannot separate cleanly, sometimes under-triggering, sometimes over-triggering, on the same class of span.

Five false positives were also observed, none of them random noise: two are generic temporal expressions plausibly mislabelled under a recall-favouring threshold, two are bare city or region names used generically inside a prompt built specifically to probe that behaviour, and one is a genuine spurious organisation detection. The gap between strict recall (0.829) and coverage recall (0.915) is consistent with the design rationale already stated in Section~\ref{subsec:impl_gliner_pivot}: the 0.45 threshold catches more entities than it assigns correct labels to, which is the expected shape of a configuration deliberately tuned toward recall over precision.

\textbf{Routing accuracy and temperature consistency.} Twenty-one prompts, six per use case plus three out-of-scope negative controls, were each run five times through the full anonymise-then-route pipeline, since the routing model runs at temperature 1.0 (Section~\ref{subsec:impl_ask_antares}) and a single pass cannot establish whether that setting produces run-to-run variation. The premise, that one sampled generation may not represent what a model does at that temperature, is the same one that motivates aggregating multiple samples rather than trusting a single generation elsewhere in LLM inference, for instance in self-consistency decoding, where the sampled variation across generations is used constructively rather than treated as noise to average away~\cite{wang2022selfconsistency}. Section~\ref{subsec:impl_ask_antares} already names the mechanism: at temperature 1.0 the model's raw output distribution is sampled unmodified~\cite{holtzman2020degeneration}, so a single trial cannot distinguish a stable routing decision from one that happened to land on the majority outcome once. Table~\ref{tab:routing_summary} reports the aggregate results: on this test set, temperature 1.0 produced no observed run-to-run routing variance.

One prompt, requesting a holiday ticket for a person with no \texttt{PULITO\_DA} cantiere assignment in the mock dataset, registered as zero correct out of five trials under the log-diffing detection method described in Section~\ref{subsec:usecases_spatial_flow}. This is the only discrepancy in Table~\ref{tab:routing_summary}, and it was checked by hand rather than re-run: reading the five response texts directly, Claude selected \texttt{report\_holiday\_request} correctly on all five repetitions, and the tool returned a legitimate business-logic failure message, since that person has no eligible cantiere, and exited before writing the log file the log-diffing method relies on. That manual read of one case supports treating the 95.2\% figure as an artefact of the detection method on this specific prompt rather than a genuine routing failure, but it is not a re-measurement across all 105 trials, and 95.2\% is therefore the routing accuracy this thesis reports as measured.

A single point estimate from 105 trials understates how much uncertainty a sample this size carries. The naive approach, a Wald interval built from the normal approximation, is known to perform badly exactly in this range, where the observed proportion sits close to 100\%~\cite{brown2001interval}; the more reliable Wilson score interval for $100/105$ gives a 95\% confidence range of roughly 89\% to 98\%. The point estimate of 95.2\% is a real, reported number, not a guess, but the underlying trial count does not support treating it as accurate to the tenth of a percentage point it is written to. A larger repeated-trials run would narrow this range; 105 trials is what this thesis's timeframe allowed.

The same routing data exposes something Table~\ref{tab:routing_summary} does not report on its own: for the canonical UC-A prompt, how many times Claude invokes \texttt{get\_nearest\_workers\_to\_cantiere} within a single \texttt{ask\_antares} call is not fixed across repetitions. Reading the five response traces individually: two repetitions call the tool three times, once per GLiNER's three fragmented location tokens (Section~\ref{subsec:arch_tokenization_redis}); two call it once, passing all three tokens concatenated into a single \texttt{cantiereName} argument; one calls it twice, merging two of the three tokens and leaving the third separate. Section~\ref{subsec:impl_ask_antares} describes the \texttt{ask\_antares} system prompt as constraining Claude to pick exactly one sub-tool per request. On this specific prompt, that constraint held, in the narrower sense of calling the underlying business tool only once, in two of the five repetitions.

Every one of the five is still scored correct in Table~\ref{tab:routing_summary}, because that metric checks only which tool ran, and the right tool ran every time. Whether each call inside a multi-call repetition independently returned a correct result is a narrower question the routing harness was not built to answer. What actually supports the final answer being right is the separate end-to-end check in Section~\ref{sec:usecases_spatial_querying} (Table~\ref{tab:uca_e2e}), which confirms the expected two workers for this prompt across two of its own repetitions, without recording how many tool calls either of those involved. The routing pass and the end-to-end pass measure different things, run on different repetitions, and neither substitutes for the other.

The routing data also explains why the multi-call repetitions did not break anything, and the explanation is not architectural luck. Deanonymisation is not something that happens once, centrally, after Claude has finished choosing a tool: \texttt{DeanonymizeAsync} is the first action of every individual business-tool invocation (Section~\ref{subsec:arch_deanonymization}), stated explicitly in the trace \texttt{architecture.tex} walks through for \texttt{GetNearestWorkersToCantiere}. So when Claude calls \texttt{get\_nearest\_workers\_to\_cantiere} three times within one \texttt{ask\_antares} call, as it does in two of the five repetitions here, it issues three separate calls to \texttt{/deanonymize-known} against the same \texttt{contextId}, not one shared call made before the tool was chosen.

Three calls against one context do not collide because of what Section~\ref{subsec:arch_anonymization_service} establishes: server-side deanonymisation reads the mapping through a non-destructive \texttt{Get}, not the one-time-use \texttt{Pop} the \texttt{IAnonymizationContextStore} interface was actually built around. A context that has already been read once is still there, unchanged, for a second and third call to read again. Each of the three fragments, \emph{Bergamo}, \emph{Via della Fonda}, and \emph{Giulia S.r.l.}, deanonymises correctly and independently identifies the same cantiere, and that is now a fully explained result rather than an open question. What it does not establish is anything about correctness under a genuinely one-time-use store: had \texttt{Pop} been the call the implementation actually uses, only the first of the three calls would have found a mapping to consume, and the other two would have returned nothing.

Using \texttt{Get} throughout removes the collision risk between repeated calls on the same context, but it does not make the fragmentation pattern itself safe in general. That three fragments happen to resolve to the same cantiere is a property of this one prompt against this one mock catalogue of three cantieri, not a guarantee the architecture provides. A differently phrased site descriptor, or a catalogue where a stray fragment partially matches a second, different cantiere, could still turn the same fragmentation pattern into multiple contradictory tool calls rather than redundant correct ones; nothing about reading a context non-destructively prevents that.

\subsection{Scope of the Validation Relative to the Research Questions}
\label{subsec:usecases_rq_mapping}

Section~\ref{sec:intro_objectives} posed three research questions before any of the results above existed. Each deserves a direct answer here, one at a time, rather than leaving the reader to infer the connection between a routing-accuracy percentage and a claim made two chapters earlier.

The first question asked what division of responsibility between client, anonymisation layer, LLM, and business-logic server structurally minimises PII exposure, as opposed to forbidding exposure by policy alone. Chapter~\ref{ch:architecture} answered this by design; this chapter is what tests whether the design holds under running conditions. Section~\ref{subsec:usecases_llm_audit}'s payload audit is the direct evidence: scanning the literal text Claude received across fifty prompts found PII in two of them, and both traced to a specific GLiNER miss rather than to a path that bypasses tokenisation altogether. That is a meaningful result, not a hedge: it shows the architecture has no independent leak path of its own, at least on the fifty prompts tested. It does not show the architecture is leak-free, and the difference matters. A structural claim was tested against fifty constructed prompts, not against the full space of ways a real user might phrase a request; a leak path this test set did not happen to construct is not a leak path this test set can rule out.

Detection was the second question: could a zero-shot, multilingual NER model reach the recall real Italian business text requires, given that the rule-based alternative had already failed on it? Section~\ref{subsec:usecases_ner_performance} answers this one most directly and most completely of the three: 93.8\% precision and 91.5\% recall on the coverage metric, with every one of the seven misses individually itemised and, following the discussion above, traced to a specific, checkable cause rather than left as an unexplained residual. This chapter does not claim 91.5\% recall is sufficient for a production deployment; whether it is depends on a risk tolerance this thesis does not set. What it claims, and what the numbers support, is that GLiNER clears the bar Presidio failed to clear, on the same kind of Italian operational text that caused that earlier failure.

The third question was about consequences: whether reversible anonymisation costs anything in correctness, on the operations that matter here. Twelve of twelve end-to-end cases across the three use cases matched an independently written reference implementation; routing accuracy measured at 95.2\%, with the one discrepancy explained as an artefact of the detection method rather than a routing error (Table~\ref{tab:routing_summary}); and the UC-A call-pattern analysis above found that even where the system's internal behaviour is less deterministic than a first read of Chapter~\ref{ch:architecture} would suggest, the final answers checked on this test set still came out right. Read together, this is evidence against a cost to \emph{final-answer} correctness on the cases exercised, not proof that no such cost exists in general, and not evidence that every internal step behaves as cleanly as the top-level result. The UC-A finding is the concrete reason to keep those two claims separate rather than treating "final answer correct" as a stand-in for "the system worked exactly as described."

None of this generalises past what was actually run. Every number in this chapter comes from a fixed mock dataset, a hand-built prompt set of fifty (detection) or twenty-one (routing) items, and a system prompt and label configuration that were set once early in the project and never systematically tuned. The three research questions are answered for this system, on this dataset, under this configuration; Chapter~\ref{ch:discussion} is where the limits of that scope, and what would need to change to extend it, are addressed directly.
