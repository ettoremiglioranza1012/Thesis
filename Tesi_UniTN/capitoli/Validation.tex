\chapter{Use Cases and Validation}
\label{ch:usecases}

Chapters~\ref{ch:architecture} and~\ref{ch:implementation} described the architecture and the implementation of Antares AI's three business use cases. This chapter validates them, against a fixed mock dataset and a purpose-built evaluation harness that exercises the running system through its real interfaces rather than its internal code paths. Section~\ref{sec:usecases_domain_overview} summarises the workforce management domain the three use cases operate on. Section~\ref{sec:usecases_spatial_querying}, Section~\ref{sec:usecases_colleague_identification}, and Section~\ref{sec:usecases_holiday_request} report end-to-end correctness for Use Cases A, B, and C respectively, against an independent reference implementation built separately from the system under test. Section~\ref{sec:usecases_validation} closes the chapter with the two cross-cutting quantitative results the privacy and correctness claims of the previous chapters were left resting on, how often PII detection fails and whether that failure ever reaches the LLM payload, how consistently the routing model selects the correct tool under its configured sampling temperature, and ends by mapping each result back to the three research questions posed in Section~\ref{sec:intro_objectives}, stating plainly what is answered and what is not.

\section{Workforce Management Domain Overview}
\label{sec:usecases_domain_overview}

Section~\ref{sec:arch_antares_ecosystem} already introduced the Antares/Miorelli domain, identifying \emph{persone}, \emph{cantieri}, and \emph{ticket} as the three core entity types, alongside the \texttt{PULITO\_DA}, \texttt{RESPONSABILE\_DI\_RIFERIMENTO}, and \texttt{AUTORIZZATORE} relations that structure the three use cases validated in this chapter. This section does not repeat that description, instead fixing the concrete dataset and scope against which every subsequent result was measured.

Every use case validated in this chapter runs against \texttt{MiorelliMockDataProvider.cs}, comprising ten persons, three cantieri, namely Bergamo, Brescia, and Mantova, the \texttt{PULITO\_DA} work assignments linking persons to cantieri, and five absence tickets, all dated within the window spanning 2026-03-28 to 2026-04-10. No production Miorelli backend and no real employee data were touched at any point during this validation, ensuring every metric in this chapter was produced against a fixed, fictional dataset, consistent with the prototype scope stated in Section~\ref{sec:impl_backend_integration}.

\section{Use Case A: Spatial Querying for Construction Sites}
\label{sec:usecases_spatial_querying}

Use Case A is validated against four test cases exercising \texttt{get\_nearest\_workers\_to\_cantiere}, including the canonical Bergamo prompt traced in Section~\ref{subsec:arch_tokenization_redis}, one case for each of the remaining two cantieri, and one case naming a nonexistent cantiere to exercise the error path.

\subsection{Haversine Distance and Radius Filtering}
\label{subsec:usecases_haversine}

Each test case is checked against an independently computed expected result rather than against the system output rederived from its own logic, addressing the test oracle problem, where a test checking system output against a value produced by the same system fails to detect shared computational faults~\cite{barr2015oracle}. Comparing two independently written implementations against each other, rather than checking one implementation output against a fixed expected value, constitutes differential testing, operating on the premise that two programs solving the same problem from different codebases are unlikely to share identical bugs~\cite{mckeeman1998differential}. The reference used for this comparison is a hand-built mirror of the mock dataset featuring its own Haversine implementation, written separately from \texttt{PersonTools.CalculateDistanceAndRank}, as detailed in Section~\ref{subsec:impl_uca}, and sharing no code with it. Before executing the full test set, the formula was spot-checked against a live server report, confirming that for the canonical Bergamo prompt at a 15\,km radius, the server logged two workers at 0.9\,km and 1.9\,km respectively, and the independent calculation matched both distances within 0.1\,km.

All four cases matched the independent reference across every repetition. The Mantova case reports no matches because both assigned workers reside outside the 15\,km radius, which the independent reference confirms as correct.

\subsection{Execution Flow and Prompt Handling}
\label{subsec:usecases_spatial_flow}

The function \texttt{ask\_antares} returns only free text to its caller, without explicitly exposing which sub-tool executed. Observability is achieved without server code modifications through the report file generated by each \texttt{JobTools} invocation within \texttt{logs/} (Section~\ref{sec:impl_jobtools}), providing a use-case-tagged, timestamped file whose name identifies the executed tool. The validation harness snapshots that directory before and after each \texttt{ask\_antares} call, identifying the new file by name to provide a reliable, zero-instrumentation mechanism for observing routing decisions externally. Section~\ref{subsec:usecases_ner_performance} reports the routing accuracy and consistency results produced by this technique for all three use cases combined, as identical methodologies and metrics apply across UC-A, UC-B, and UC-C.

\section{Privacy and Functional Validation}
\label{sec:usecases_validation}

The preceding three sections validated business-logic correctness, while this section validates the two claims that Chapters~\ref{ch:architecture} and~\ref{ch:implementation} left open pending measurement, namely whether PII actually reaches the LLM payload in practice, and how accurately and consistently the routing model selects the correct tool given its configured sampling temperature. Both were measured against the running system through its real interfaces, rather than against internal code paths, over a fifty-prompt Italian test set built for this purpose.

\subsection{Auditing the LLM Context Boundary}
\label{subsec:usecases_llm_audit}

Section~\ref{sec:arch_privacy_by_design} states the structural claim directly, establishing that PII isolation holds only for entities the detection layer actually finds. This section reports the measurement behind that claim, determining how often GLiNER misses a real PII entity and whether a missed entity actually reaches the context of Claude.

\texttt{AntaresTools.AskAntares} sends Claude exactly two messages per call, consisting of a static Italian system prompt, unchanged except for the \texttt{context\_id} it carries, and a user message equal to whatever \texttt{user\_input} string the caller supplied. Because the validation harness acts as that caller, it constructs \texttt{user\_input} itself, making the exact literal payload received by Claude fully reconstructable client-side without requiring server-side logging, instrumentation, or code modifications. That reconstructed payload was scanned across all fifty test prompts for any of thirty-nine known real PII values drawn from the mock dataset, including full names, phone numbers, email addresses, and full site or company descriptors.

Two leaks were identified out of fifty scanned prompts, corresponding to an email address in one prompt and a different email address in another, representing cases where GLiNER failed to tag the address within its specific sentence context. Both leaks correlate with a GLiNER false negative reported in Section~\ref{subsec:usecases_ner_performance}, and no leak occurred without corresponding to a detection miss. This supports the structural claim in Section~\ref{sec:arch_privacy_by_design}, demonstrating that the anonymisation layer possesses no independent bypass path, and the privacy guarantee provided by this architecture reduces entirely to detection recall. Each entry in the false-negative list below constitutes a specific, confirmed PII leak path rather than a general statement regarding NER quality.

\subsection{Routing Accuracy and NER Performance in Italian}
\label{subsec:usecases_ner_performance}

\textbf{PII detection.} PII detection was evaluated using fifty hand-built Italian prompts carrying eighty-two labelled entity spans against the live \texttt{/anonymize} endpoint at its production configuration from Section~\ref{subsec:impl_gliner_pivot}, utilising the real GLiNER-based detection path, a threshold of 0.45, and the full eight-label set. Two metrics are reported, specifically \emph{coverage}, determining whether a PII substring was tokenised regardless of predicted label accuracy, which governs whether PII can leak, and \emph{strict}, standard span-and-label NER evaluation following the CoNLL-2003 shared task framework~\cite{tjongkimsang2003conll}. The coverage/strict distinction follows an older evaluation precedent from the MUC-6 shared task, which scored NER systems under both exact and relaxed matches, crediting correct spans despite wrong predicted labels, preventing aggregated scoring from concealing specific error types~\cite{sundheim1995muc6}. Here, that distinction separates privacy failures, measured by coverage, from merely mislabelled yet still-masked entities, measured strictly.

Seven entities were missed entirely under the coverage metric, itemised in Table~\ref{tab:gliner_fn}. Two comprised email addresses missed mid-sentence, already identified in Section~\ref{subsec:usecases_llm_audit} as the two payload leaks and marked accordingly. Four share a single pattern involving Italian date-range expressions structured as \emph{``dal X al Y aprile''}. The seventh, a bare cantiere-city reference of \emph{Brescia} embedded within a longer compound site descriptor, does not fit that pattern and is treated separately.

Classifying date-range misses merely as an Italian-language weakness lacks precision, whereas the four instances in Table~\ref{tab:gliner_fn} support a narrower, checkable explanation. A range expression like \emph{``dal 3 al 7 aprile''} designates two numeric endpoints and one shared month across a five-token span joined by prepositions rather than adjacency. A single date like \emph{``il 3 aprile''} or \emph{``il 07/04/2026''} forms a contiguous, self-contained span that zero-shot conditioning enables GLiNER to recognise from a short label description. The label set requested by the Anonymisation Service, detailed in Section~\ref{subsec:impl_gliner_pivot}, offers only a bare \texttt{"date"} label, providing no instruction that two dates joined by \emph{dal} or \emph{al} should form a single entity rather than two separate, weaker mentions or no entity at all. Five false positives reported in Table~\ref{tab:gliner_metrics} include two temporal expressions successfully flagged by the model, arguing against general blindness to Italian date phrasing and pointing towards a narrower cause, where single dates and generic temporal phrases exceed the detection threshold while five-token range constructions built from two components do not. This represents the most likely explanation given available data, as direct testing would require adding an explicit \texttt{"date range"} or \texttt{"periodo"} label at inference time and re-running the test set, which was outside the scope of this thesis. The broader pattern indicates that span-based models underperform on entities composed of multiple linked pieces rather than contiguous mentions, aligning with literature on discontinuous entities where contiguous-decoding assumptions create difficulty~\cite{dai2020discontinuous}. Absence-period phrasing of this shape appears in real Use Case~C holiday requests, as noted in Section~\ref{sec:usecases_holiday_request}, making missed date ranges a concrete risk rather than a hypothetical concern, matching the failure mode measured on this test set.

The seventh miss, \emph{Brescia}, represents a different failure mode excluded from the date-range explanation. Prompt B4 names the cantiere as \emph{``Brescia Via Risorgimento 8''}, where GLiNER tokenised \emph{Via Risorgimento 8} as \texttt{<LOCATION\_0001>} while leaving the leading city name untouched. Conversely, Table~\ref{tab:gliner_metrics}'s false positives include the opposite error on prompt C5, where \emph{Bergamo} is flagged as a location when the sentence explicitly contrasts the city from the eponymous cantiere. Together, these results demonstrate that GLiNER decisions on bare city names swing on sentence-level context beyond the control of a single confidence threshold, leading to occasional under-triggering or over-triggering within the same entity class.

Five false positives observed include non-random instances, specifically two generic temporal expressions mislabelled under a recall-favoring threshold, two bare city or region names used generically in probing prompts, and one genuine spurious organisation detection. The gap between strict recall at 0.829 and coverage recall at 0.915 aligns with the design rationale of Section~\ref{subsec:impl_gliner_pivot}, where a threshold of 0.45 captures more entities than it correctly labels, reflecting a configuration deliberately tuned for recall over precision.

\textbf{Routing accuracy and temperature consistency.} Routing accuracy and temperature consistency were evaluated using twenty-one distinct prompts comprising six per use case plus three out-of-scope negative controls, run five times each through the complete anonymise-then-route pipeline. Because the routing model operates at temperature 1.0, as stated in Section~\ref{subsec:impl_ask_antares}, single passes cannot establish whether run-to-run variations occur, mirroring motivations for aggregating multiple samples in techniques like self-consistency decoding~\cite{wang2022selfconsistency}. At temperature 1.0, raw output distributions are sampled unmodified~\cite{holtzman2020degeneration}, preventing single trials from distinguishing stable routing decisions from majority outcomes occurring by chance. Aggregate results demonstrate that temperature 1.0 produced no observed run-to-run routing variance across this test set.

One prompt, requesting a holiday ticket for a person with no \texttt{PULITO\_DA} cantiere assignment in the mock dataset, registered as zero correct out of five trials under the log-diffing detection method described in Section~\ref{subsec:usecases_spatial_flow}. This is the only discrepancy in Table~\ref{tab:routing_summary}, and it was checked by hand rather than re-run: reading the five response texts directly, Claude selected \texttt{report\_holiday\_request} correctly on all five repetitions, and the tool returned a legitimate business-logic failure message, since that person has no eligible cantiere, and exited before writing the log file the log-diffing method relies on. That manual read of one case supports treating the 95.2\% figure as an artefact of the detection method on this specific prompt rather than a genuine routing failure, but it is not a re-measurement across all 105 trials, and 95.2\% is therefore the routing accuracy this thesis reports as measured.

A single point estimate derived from 105 trials carries inherent uncertainty, and naive Wald intervals derived from normal approximations perform poorly when observed proportions approach 100 percent~\cite{brown2001interval}. The more reliable Wilson score interval for 100 out of 105 trials yields a 95 percent confidence range spanning roughly 89 percent to 98 percent. While 95.2 percent represents a reported point estimate rather than a guess, the underlying trial count does not support accuracy down to tenths of a percentage point, though 105 trials represented the limit permitted by the project timeframe.

The routing data reveals additional behaviors not captured in Table~\ref{tab:routing_summary}, such as varying invocation counts for \texttt{get\_nearest\_workers\_to\_cantiere} during a single \texttt{ask\_antares} call for the canonical UC-A prompt. Analysis of the five response traces indicates that two repetitions invoke the tool three times, corresponding to GLiNER's three fragmented location tokens from Section~\ref{subsec:arch_tokenization_redis}, two repetitions invoke the tool once, passing all tokens concatenated into a single \texttt{cantiereName} argument, and one repetition invokes the tool twice, merging two tokens and leaving the third separate. Section~\ref{subsec:impl_ask_antares} describes the \texttt{ask\_antares} system prompt as constraining Claude to select exactly one sub-tool per request, a constraint met in the narrower sense of invoking the underlying business tool once in only two of the five repetitions.

All five repetitions achieve correct scoring in Table~\ref{tab:routing_summary} because the metric checks only which tool executed, and the correct tool executed consistently. Whether each individual call within a multi-call repetition returned correct results is a narrower question outside the scope of the routing harness, supported instead by the independent end-to-end check in Section~\ref{sec:usecases_spatial_querying} (Table~\ref{tab:uca_e2e}), which confirms expected worker counts across repetitions without tracking tool invocation counts. Routing passes and end-to-end passes measure distinct properties across different repetitions without substituting for one another.

The routing data explains why multi-call repetitions remained stable without architectural luck. Deanonymisation does not occur centrally after tool selection, because \texttt{DeanonymizeAsync} serves as the initial action of every individual business-tool invocation (Section~\ref{subsec:arch_deanonymization}), as detailed in the trace \texttt{architecture.tex} walks through for \texttt{GetNearestWorkersToCantiere}. Consequently, when Claude invokes \texttt{get\_nearest\_workers\_to\_cantiere} three times within a single \texttt{ask\_antares} call, it issues three separate calls to \texttt{/deanonymize-known} against the same \texttt{contextId} rather than a single shared call.

Three calls against one context avoid collisions due to the mechanism established in Section~\ref{subsec:arch_anonymization_service}, where server-side deanonymisation reads mappings via non-destructive \texttt{Get} operations rather than one-time-use \texttt{Pop} executions. Contexts read once remain intact for subsequent read operations. Each of the three fragments, namely \emph{Bergamo}, \emph{Via della Fonda}, and \emph{Giulia S.r.l.}, deanonymises correctly and identifies the same cantiere independently, explaining the observed outcome. However, this does not guarantee safety under a genuine one-time-use store, where utilising \texttt{Pop} would cause subsequent calls to return nothing after the first consumption.

Using \texttt{Get} throughout removes collision risks during repeated calls on identical contexts, but it does not render fragmentation safe in general. That three fragments resolve to the same cantiere stems from the specific mock catalogue of three cantieri rather than an architectural guarantee. Differently phrased site descriptors or catalogues where stray fragments partially match secondary cantieri could transform fragmentation patterns into contradictory tool calls rather than redundant correct ones, a risk unmitigated by non-destructive context reads.

\subsection{Scope of the Validation Relative to the Research Questions}
\label{subsec:usecases_rq_mapping}

Section~\ref{sec:intro_objectives} posed three research questions before any of the preceding results existed, and each deserves a direct answer here rather than leaving the reader to infer connections between routing accuracy percentages and claims established two chapters earlier.

The first question investigated the division of responsibility between client, anonymisation layer, LLM, and business-logic server required to structurally minimise PII exposure, as opposed to forbidding exposure through policy alone. Chapter~\ref{ch:architecture} addressed this architecturally, while this chapter examines whether the design holds under runtime conditions. The payload audit in Section~\ref{subsec:usecases_llm_audit} provides direct evidence, as scanning the literal text received by Claude across fifty prompts revealed PII in two instances, both tracing to specific GLiNER detection misses rather than bypass pathways. This demonstrates that the architecture contains no independent leak paths on the tested prompts. However, this does not prove the system is entirely leak-free, because the structural claim was evaluated against fifty constructed prompts rather than the full space of phrasing variations a real user might employ, meaning unconstructed leak paths cannot be ruled out.

The second question addressed detection capabilities, asking whether a zero-shot multilingual NER model could reach practically usable recall on real Italian business text after rule-based alternatives failed. Section~\ref{subsec:usecases_ner_performance} answers this comprehensively, reporting 93.8\% precision and 91.5\% recall on coverage metrics, with all seven misses itemised and traced to checkable causes rather than unexplained residuals. This work does not claim 91.5\% recall suffices for production deployments, as adequacy depends on organisational risk tolerances outside the scope of this thesis. Instead, the data supports the claim that GLiNER clears the operational hurdle where Presidio failed on identical Italian texts.

The third question examined consequences, specifically whether reversible anonymisation imposes correctness costs on critical operations. Twelve end-to-end cases across three use cases matched independent reference implementations, and routing accuracy reached 95.2\%, with the single discrepancy explained as a detection-method artefact rather than a routing error (Table~\ref{tab:routing_summary}). The UC-A call-pattern analysis shows final answers remained correct despite internal execution non-determinism (Section~\ref{sec:usecases_spatial_querying}). This is not a complete answer, though. All four UC-C cases ran outside the mock dataset's active absence-ticket window (Section~\ref{sec:usecases_holiday_request}), so what was measured is UC-C's authorisation logic, rather than its absence-coverage and substitution-chain logic, which never executed against a live absence in this validation run. Within that scope, the evidence weighs against a correctness cost for reversible anonymisation, and it does not establish the absence of one across paths this validation never exercised.

None of these results generalise beyond the executed scope, as every metric derives from a fixed mock dataset, hand-built prompt sets of fifty items for detection and twenty-one for routing, and a static system prompt configuration established early in the project without systematic tuning. The three research questions find answers specific to this system, dataset, and configuration, while Chapter~\ref{ch:discussion} addresses the limits of this scope and the modifications required for extension.
