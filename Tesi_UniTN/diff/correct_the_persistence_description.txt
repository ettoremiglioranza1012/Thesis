PROFESSOR FEEDBACK POINT 4: "Correct the persistence description"
================================================================================

Scope: every "ephemeral"/"short-lived" claim about the Redis token-map
context was factually wrong on the failure path (no TTL is configured;
`Pop` only removes a mapping on the success path). Reworded to state the
mechanism accurately (Pop-on-consumption is real) and name the gap
explicitly (no TTL, so an errored/abandoned request's mapping persists
indefinitely). Also flagged, for the first time anywhere in the thesis,
that the per-request log files are themselves a persistent, unencrypted,
access-uncontrolled PII record on local disk.

Text-only pass: no code change. Adding a TTL to the Redis `Store` call was
considered and explicitly deferred as optional, per direction — the
thesis states the gap honestly instead of fixing it in the implementation.

Policy change starting this pass: previously, limitations requiring new
Chapter 6 (discussion.tex) prose were drafted but left uninserted, because
that chapter was entirely `\iffalse`'d and chapter-writing was paused.
From this point forward, when a rewording pass surfaces a limitation that
belongs in the discussion chapter, it gets written in during that same
pass rather than deferred. This pass is the first to do that: it opens
discussion.tex with its chapter-level roadmap paragraph (required by the
project's chapter-opening-paragraph convention, since this is the first
prose the chapter has ever had) and un-`\iffalse`s Section 6.1 only,
leaving 6.2-6.4 disabled until their own content is ready.

FILE: capitoli/architecture.tex
CHAPTER/SECTION: Section 3.1, "Architectural Principles: Privacy-by-Design"
(End-to-end security bullet)
================================================================================

--- OLD ---
\textbf{End-to-end security.} The token-to-entity mapping is stored in an
ephemeral, session-scoped Redis context and consumed exactly once during
server-side deanonymisation. No component persists PII beyond the minimum
lifetime required for a single business operation. Operational reports
written to disk by the \texttt{JobTools} layer stay on server-local
storage and are never sent to the client.

--- NEW ---
\textbf{End-to-end security.} The token-to-entity mapping is stored in a
session-scoped Redis context; on the path where a business operation
completes, it is consumed exactly once during server-side deanonymisation
and removed. That removal is not currently guaranteed independent of that
path: no time-to-live is configured on the context, so a mapping tied to
a request that errors out before deanonymisation persists in Redis
indefinitely, a prototype-scope limitation discussed in
Chapter~\ref{ch:discussion}. Operational reports written to disk by the
\texttt{JobTools} layer, containing real names and phone numbers, stay on
server-local storage and are never sent to the client, but are themselves
a persistent, unencrypted record with no retention policy applied.

--- WHY ---
This is the Cavoukian "end-to-end security" principle bullet — the most
consequential instance of the claim, since everything else inherits from
it. Split the happy-path mechanism (real, accurate) from the actual
guarantee (none, absent a TTL), and added the log-file persistence gap
that was previously stated as fact but never flagged as a limitation.

CHAPTER/SECTION: Section 4.2.3, closing sentence
--------------------------------------------------------------------------------

--- OLD ---
Server-side deanonymisation always uses \texttt{Pop}, not \texttt{Get}, so
a context can be consumed exactly once. This is a direct implementation of
the end-to-end security principle from Chapter~\ref{ch:architecture}: the
mapping does not simply expire eventually, it stops existing the instant
it has served its one legitimate purpose.

--- NEW ---
Server-side deanonymisation always uses \texttt{Pop}, not \texttt{Get}, so
a context is removed the instant it is actually consumed, rather than
lingering after it has served its purpose. That guarantee covers only the
path where \texttt{Pop} is actually called: no time-to-live is configured
on the Redis context itself, so a request that errors out before
deanonymisation, or a client session that is never completed, leaves its
mapping in Redis with no expiry. This is a deliberate scope decision
rather than an oversight, discussed in full in Chapter~\ref{ch:discussion}:
the system runs as a local proof of concept, with no persistence volume
mounted on Redis, so every mapping is cleared the moment the process stops
regardless, and what the internship needed to demonstrate was that
pseudonymisation and its MCP-based orchestration work correctly end to
end, not a production-grade retention policy.

--- WHY ---
This was the single worst-offending sentence in the thesis on this point:
"the mapping does not simply expire eventually, it stops existing the
instant it has served its one legitimate purpose" is true only on the
happy path, and actively wrong on the failure path (it does simply
persist indefinitely, exactly the "eventually" framing it denies). Fully
rewritten to state the real mechanism, the real gap, and the reasoning
behind not closing it, matching the PoC-scope justification given to the
supervisor.
