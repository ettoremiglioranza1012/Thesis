# MCP Client — `Antares_AI_McpClient`

**Type:** Console application  
**Framework:** .NET 10  
**Role:** Reference implementation and test harness for the MCP server. Demonstrates the full anonymize → route → respond flow for all three use cases (UC-A, UC-B, UC-C).

---

## Purpose

The client is **not** a production UI — it is the integration test runner and a concrete reference for how any real client (web app, mobile app, internal tool) should interact with this architecture. It shows:

1. How to anonymize a prompt before sending it to the server
2. How to pass `contextId` through `ask_antares` so the server can deanonymize
3. That the client response contains **no PII** — only a hardcoded confirmation string from the server

---

## Entry Point — `Program.cs`

Bootstraps the application:

1. Registers a named `HttpClient` for the Anonymization Service (`AnonymizationClient` → `http://localhost:5292`)
2. Creates an `McpClient` connected to the MCP Server at `http://localhost:5001/sse` (SSE transport)
3. Instantiates `AppRunner` and calls `Run(client)`

---

## `App/AppRunner.cs`

The `AppRunner` class contains the three use case runners. All three follow the same four-step pattern.

### The 4-Step Pattern (for every use case)

```
Step A: Build the original plain-text prompt
Step B: Anonymize the prompt → get anonymized text + contextId
Step C: Call ask_antares(anonymized_text, contextId)
Step D: Print the server's response (hardcoded string only)
```

### Step B in detail

```csharp
var anonResult = await presClient.AnonymizeAsync(originalPrompt);
var anonymizedPrompt = anonResult.Text ?? originalPrompt;
var contextId        = anonResult.ContextId;
```

- Calls `GET /anonymize?input=<prompt>` on the Anonymization API
- `anonResult.Text` — the prompt with PII replaced by tokens
- `anonResult.ContextId` — the Redis key that maps tokens back to real values
- `anonResult.KnownFieldCount` — how many distinct entities were found

If `contextId` is null (no PII detected), the original prompt is forwarded as-is. This is safe because the server will skip deanonymization when `context_id` is null.

### Step C in detail

```csharp
var mcpResult = await client.CallToolAsync(
    "ask_antares",
    new Dictionary<string, object?>
    {
        { "user_input", anonymizedPrompt },
        { "context_id", contextId }
    });

var response = ((TextContentBlock)mcpResult.Content[0]).Text;
```

The MCP client calls the `ask_antares` tool with the anonymized prompt. The server's Claude-generated response is extracted from the first content block.

## Use Case Scenarios

### UC-A — `RunUcA`

**Prompt:** `"Trova i lavoratori più vicini al cantiere Bergamo Via della Fonda 5 Giulia S.r.l. entro 15 km. Risolvi tutti i GUID internamente."`

After anonymization, the location name becomes `<LOCATION_0001>`. Claude routes to `get_nearest_workers_to_cantiere`. The server deanonymizes, finds and ranks PULITO_DA workers, logs the report, and returns `"Operazione completata con successo."`.

### UC-B — `RunUcB`

**Prompt:** `"Trova i colleghi di Giulia Conti. Risolvi tutti i GUID internamente."`

After anonymization, the person name becomes `<PERSON_0001>`. Claude routes to `get_colleagues_of_person`. The server finds colleagues and the top-5 nearest non-colleagues, logs the report.

### UC-C — `RunUcC`

**Prompt:** `"Il mio nome è Giulia Conti e voglio aprire un ticket ferie. Risolvi tutti i GUID internamente."`

After anonymization, `Giulia Conti` → `<PERSON_0001>`. Claude routes to `report_holiday_request`. The server checks authorization, finds absent colleagues and nearby workers, logs the report.

## What a Real Client Would Do Differently

The `AppRunner` is intentionally simple. A production client would:

1. Accept dynamic user input instead of hardcoded strings
2. Handle the `contextId` lifecycle (possibly across multiple turns of a conversation)
3. Display the anonymized token names in the UI (e.g., show `<PERSON_0001>` as a placeholder, not the real name)
4. Implement proper error handling and retry for network failures
5. Use the SSE stream for real-time progress updates during long tool calls
